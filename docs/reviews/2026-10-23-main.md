# Review, main, 2026-10-23

**Reviewed by**: Gemini Pro (author on Gemini Flash)
**Scope**: 19 files, main vs HEAD~1
**Verdict**: Blocked

## Summary
This change implements a full-featured ecommerce storefront demonstration connecting Next.js App Router with Stripe Hosted Checkout in test mode and browser local storage persistence. The storefront UI, credentials drawer, catalog data model, and visual styling are exceptionally clean, responsive, and thoughtfully designed. However, merge is blocked by an infinite HTTP fetch loop upon return from Stripe checkout on `/orders/[id]`, alongside significant security and contract issues including a missing sandbox test-key validation guard on the verification API, absence of order ID validation against Stripe session metadata, and an order total mismatch where UI tax is displayed but omitted from Stripe charges.

## Blockers
### 🔴 Infinite HTTP fetch loop on payment confirmation, `app/orders/[id]/page.tsx:47`
**Problem**: The payment verification `useEffect` in `OrderDetailsContent` includes unstable function references (`updateOrderStatus`, `clearCart`, `saveOrder`) in its dependency array. Inside the effect, calling `updateOrderStatus` triggers state updates in `OrdersProvider`, which causes `OrdersProvider` to re-render and re-instantiate new function instances for `updateOrderStatus` and `saveOrder`. In turn, this triggers the `useEffect` to execute again on every render cycle without any memoization, `useRef` run-once guard, or check against existing `"paid"` order state.
**Why it matters**: Whenever a customer completes payment and Stripe redirects back to `/orders/[id]?session_id={CHECKOUT_SESSION_ID}`, the client enters an infinite loop spamming GET requests to `/api/checkout/verify` and upstream Stripe API endpoints (`stripe.checkout.sessions.retrieve`). This rapidly exhausts Stripe rate limits (HTTP 429), churns CPU and memory, causes continuous UI flickering, and risks locking up the customer's browser tab.
**Suggested fix**: Wrap context helper functions (`updateOrderStatus`, `saveOrder`, `getOrderById`, `clearCart`) in `useCallback` in their respective providers, and guard the verification effect in `app/orders/[id]/page.tsx` with a `useRef` flag (e.g., `hasVerifiedRef`) or bail out immediately if the loaded order already has `paymentStatus === "paid"`.

## Major
### 🟠 Missing `sk_test_` sandbox key guard on session verification endpoint, `app/api/checkout/verify/route.ts:21`
**Problem**: While `POST /api/checkout` strictly validates that the secret key starts with `sk_test_`, `GET /api/checkout/verify` only checks if `secretKey` is truthy and completely omits the sandbox prefix check before initializing the Stripe client.
**Why it matters**: Violates Spec 0001's core invariant and security rule that only Stripe test keys are accepted and production live keys are rejected by validation guards. A live key inadvertently supplied in header `x-stripe-secret-key` would be executed directly against Stripe's production API.
**Suggested fix**: Replicate the sandbox prefix validation check from `POST /api/checkout` into `GET /api/checkout/verify`, returning a 400 Bad Request if the key does not start with `sk_test_`.

### 🟠 Missing Order ID validation against Stripe session metadata, `app/orders/[id]/page.tsx:75`
**Problem**: When `/api/checkout/verify` returns `paid: true`, `app/orders/[id]/page.tsx` unconditionally updates the status of the route parameter `orderId` to `"paid"`. It does not compare the session's recorded order reference (`data.orderId`) with `orderId`.
**Why it matters**: Introduces an IDOR / session substitution vulnerability in client storage. A customer or test operator can mark any arbitrary pending order as paid simply by appending a valid paid `session_id` from a different transaction to the URL (`/orders/[targetId]?session_id=[otherPaidSessionId]`).
**Suggested fix**: In `app/orders/[id]/page.tsx`, verify that `data.orderId === orderId` before transitioning order status to paid. If they do not match, set a verification error and abort the update.

### 🟠 Discrepancy between UI checkout total (with estimated tax) and Stripe charge amount, `context/CartContext.tsx:83`, `app/checkout/page.tsx:325`, `app/api/checkout/route.ts:74`
**Problem**: The cart and checkout UI compute an estimated 8% tax and present an order total including tax (e.g. $322.92 for a $299.00 item) on the "Pay with Stripe" button. However, `POST /api/checkout` constructs line items exclusively from catalog base prices and sends no tax line item or Stripe `automatic_tax` configuration.
**Why it matters**: When redirected to Stripe Hosted Checkout, the customer is presented with and charged only the subtotal ($299.00). Upon returning to the receipt page, the recorded draft order and verified Stripe charge disagree, breaking financial consistency between what the user authorized and what Stripe billed.
**Suggested fix**: Align the checkout calculation and Stripe session configuration: either append the calculated tax as a distinct line item to the Stripe checkout session, enable Stripe `automatic_tax`, or eliminate the mock 8% tax calculation so that the storefront total matches the exact subtotal charged by Stripe.

## Minor
### 🟡 Hardcoded `payment_method_types: ["card"]` in Checkout Session creation, `app/api/checkout/route.ts:112`
**Problem**: Line 112 hardcodes `payment_method_types: ["card"]` when calling `stripe.checkout.sessions.create`.
**Why it matters**: Directly violates the repository's `.agents/skills/stripe-best-practices/references/payments.md` guide, which instructs developers to never hardcode `payment_method_types: ['card']` on Checkout Sessions, as omitting it enables Stripe dynamic payment methods (Apple Pay, Google Pay, Link, etc.).
**Suggested fix**: Omit `payment_method_types` from `stripe.checkout.sessions.create` to allow Stripe to automatically present optimal payment methods configured in the dashboard.

### 🟡 Fragile origin and referer handling for Checkout redirect URLs, `app/api/checkout/route.ts:103`
**Problem**: When deriving `cleanOrigin`, the handler falls back to `req.headers.get("referer")`. Unlike `Origin`, the `Referer` header contains the full path (e.g., `http://localhost:3000/checkout`). Stripping trailing slashes still leaves the pathname, resulting in malformed URLs like `http://localhost:3000/checkout/checkout?canceled=true`.
**Why it matters**: If a client request omits the `Origin` header (common with certain proxies or non-browser clients), the return redirect URLs from Stripe Hosted Checkout will have duplicated paths leading to 404 errors upon completion or cancellation.
**Suggested fix**: Parse the URL safely using `new URL(origin).origin` or `new URL(req.url).origin` to ensure only the protocol, hostname, and port are extracted.

### 🟡 Orphaned pending draft orders upon checkout cancellation, `app/checkout/page.tsx:165`
**Problem**: Initiating checkout saves a draft order with `paymentStatus: "pending"`. When a user cancels on Stripe and returns to `/checkout?canceled=true`, the app displays the cancellation notice but never transitions the pending draft order to `"canceled"` or removes it from `OrdersContext`.
**Why it matters**: Spec 0001 state transitions require: *"If canceled, status marked canceled or removed"*. Failing to handle this leaves abandoned draft orders permanently in `/orders` history.
**Suggested fix**: Include `order_id` in `cancel_url` (`/checkout?canceled=true&order_id=${orderId}`), and when `canceled=true`, invoke `updateOrderStatus(orderId, "canceled")` or remove the draft record.

### 🟡 Instant Buy leaves Cart Drawer open over `/checkout` page, `app/products/[id]/page.tsx:53`
**Problem**: In `handleInstantBuy`, calling `addToCart(product, quantity)` sets `isCartOpen = true`. The component immediately executes `router.push("/checkout")` without closing the drawer.
**Why it matters**: When the user arrives on `/checkout`, the slide-out `CartDrawer` remains open and obscures the checkout summary until dismissed.
**Suggested fix**: Explicitly call `setIsCartOpen(false)` inside `handleInstantBuy`, or pass an option to `addToCart` suppressing drawer opening.

### 🟡 Stale closure and direct state mutation in context providers, `context/OrdersContext.tsx:34`, `context/CartContext.tsx:43`
**Problem**: In `OrdersContext.tsx`, `saveOrder` and `updateOrderStatus` reference `orders` directly from the component scope rather than using functional state updater callbacks (`setOrders(prev => ...)`). In `CartContext.tsx` line 43, `updated[existingIndex].quantity += quantity` mutates the nested cart item object directly before setting state.
**Why it matters**: Rapid state transitions can drop updates due to stale closures, and mutating objects in React state violates immutability guarantees, risking missed re-renders.
**Suggested fix**: Refactor state updates to use `setOrders(prev => ...)` and ensure full shallow copying when updating nested objects (`updated[existingIndex] = { ...updated[existingIndex], quantity: ... }`).

## Nits
- ⚪ `components/CredentialsDrawer.tsx:86`: The status badge checks `config.isConfigured` rather than `hasValidKeys`, displaying a green "Client Keys Configured" badge even when invalid or non-sandbox keys are present.
- ⚪ `components/CredentialsDrawer.tsx:48`: `navigator.clipboard.writeText` is unhandled and will throw an unhandled promise rejection in restricted iframe or non-secure contexts; attach `.catch(() => {})`.
- ⚪ `app/api/checkout/verify/route.ts:36`: The endpoint expands `line_items` from Stripe but omits them from the JSON response payload, incurring unnecessary data transfer that is never consumed.

## Strengths
- **Exemplary UI Craftsmanship**: The storefront layout, catalog grid, product detail page, and drawer components showcase exceptional attention to typography, spacing, and micro-interactions aligned with the ATELIER aesthetic.
- **Robust Defense Against Client Price Tampering**: `POST /api/checkout` independently resolves and validates all item pricing against canonical catalog records rather than trusting client-submitted prices.
- **Frictionless Developer Testing Experience**: The on-screen credentials drawer with test card copy utilities and dynamic header badges makes testing the Stripe sandbox exceptionally intuitive without needing server restarts.

## Resolution of Findings (2026-10-23)

* **Infinite fetch loop fixed**: Wrapped `updateOrderStatus`, `saveOrder`, and `clearCart` in `useCallback` in their context providers. Added a `useRef` run once guard in `app/orders/[id]/page.tsx` preventing duplicate verification passes.
* **Sandbox key validation added**: `GET /api/checkout/verify` now enforces `sk_test_` prefix checking matching `POST /api/checkout`.
* **Session Order ID security check**: `app/orders/[id]/page.tsx` now verifies that the Stripe session order reference matches the route parameter before marking status as paid.
* **Pricing alignment**: Storefront checkout subtotal now matches the Stripe charged amount exactly.
* **Dynamic payment methods enabled**: Omitted hardcoded `payment_method_types: ["card"]` in `app/api/checkout/route.ts` to allow dynamic payment methods per Stripe best practices.
* **Clean origin parsing**: Derives URL origin safely without duplicating route paths.
* **Draft order cancellation**: Automatically updates draft orders to canceled status when returning from a canceled Stripe checkout.
* **Instant buy drawer fix**: Closes CartDrawer when navigating directly to checkout.
